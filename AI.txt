AI USAGE STATEMENT — Personal Workplanner - Matt Schmuecker
==========================================

I figured it was helpful to just have the AI model explain the extent of how it operated but I generally took the approach that the below outlines of allowing the AI tool to serve as the programmer. I outlined using typescript and modularizing the components (it originally put them into one large tsx file). This actually allows me to understand and review the code in a way that I would expect. I also want typescript to have better typing/object completion/etc since it sets up a better future for adding to the tool/debugging/understanding, etc. The AI had a lot of troubles with getting proportions and balancing of the UI to be effective and initially made some silly choices in its user inputs it expected so I refined those and cut out a lot of necessary, tangential features and streamline it more towards a somewhat simple workplanning tool. AI added a lot of value in hooking up the Netlify Identity auth workflow and persisting that through the application.


Summary
-------
This project was built through AI-assisted "pair programming." Essentially all
of the source code was written by an AI coding assistant, working under the
continuous direction, review, and testing of the human developer. The human
acted as product owner, architect-of-intent, tester, and final decision-maker;
the AI acted as the implementing engineer.


Approximate share of the codebase that is AI-generated
------------------------------------------------------
~95–100% of the committed code (TypeScript/React, CSS, Netlify function,
config, and documentation) was generated by the AI assistant. A realistic
single number is roughly 98%.

The remaining human-authored portion is small and mostly non-code:
 - A few direct text edits (e.g., adding the production URL and notes to
   README.md).
 - Configuration performed outside the repo (GitHub repository, Netlify site
   and Identity settings, and Microsoft Azure app registration values), which
   the human set up and then supplied to the AI.

Note: even where the AI produced the code, the human chose *what* to build,
*how it should behave*, and *whether it was acceptable*, so "AI-generated" here
means "typed by the AI," not "decided by the AI."


What AI was used
----------------
 - Tool: Claude Code (Anthropic's agentic coding CLI).
 - Model: Claude Opus 4.8.
 - Mode of use: a natural-language conversation in which the AI read and edited
   files directly, ran the production build (`npm run build`) to verify each
   change, used git, and diagnosed/fixed deployment issues. For several larger
   features the AI dispatched background sub-agents to implement changes in
   parallel, which the primary AI then reviewed and build-verified.


What the AI did (its role)
--------------------------
 - Implemented the full front end (React + TypeScript + Vite): the weekly plan,
   daily view, live start/stop timers, manual time entry, multi-day tasks,
   task create/edit modal, review and manager views, capacity/readiness
   indicator, collapsible summary, week history with carry-over, and week
   navigation.
 - Implemented persistence: a Netlify Function backed by Netlify Blobs for
   authenticated per-user storage, with a local-storage fallback, plus data
   migrations to keep older saved data working.
 - Implemented the calendar (.ics) import pipeline, including a dependency-free
   ICS parser and mapping Outlook categories to app sections.
 - Modularized the codebase into lib/, hooks/, and components/.
 - Diagnosed and fixed real problems: a broken/empty git repo, a Netlify build
   failure caused by internal package-registry URLs, a Netlify Identity
   misconfiguration, and several UI layout bugs.
 - Analyzed authentication/integration options (Netlify Identity, Microsoft
   Graph single- vs multi-tenant) and explained trade-offs.
 - Wrote the project documentation (README, an HTML project overview, and a
   Microsoft Graph integration handoff doc).


What the human did (their role)
-------------------------------
 - Defined the product: the purpose (compare planned vs. actual vs. unplanned
   work) and prioritized every feature.
 - Made the key decisions: hosting on Netlify, the authentication approach,
   choosing a multi-tenant Microsoft Graph model so the app can work for people
   outside the organization, feature scope and ordering, and UX direction.
 - Reviewed and tested: exercised the deployed site, caught issues (e.g., an
   unusable import dialog identified from a screenshot), and required that
   changes be built and reviewed before being pushed.
 - Handled all external setup: GitHub repository, Netlify deploy and Identity,
   and the Microsoft Azure / Office 365 Graph access needed for the calendar
   integration.
 - Steered iteration: gave feedback ("make the color choice smaller," "move
   this into the header," "the dropdown gets unwieldy over a year") that drove
   successive refinements.


Verification
------------
Every AI change was verified by a successful production build, and the human
independently reviewed and tested behavior in the browser / on the deployed
site before it was accepted. Correctness and final judgment remained with the
human developer.


How data storage works (Netlify Blobs)
--------------------------------------
The app stores each user's data with Netlify Blobs, a simple key/value object
store that Netlify provisions automatically for a site — there is no database
to set up, no connection string, and no separate credentials to manage.

Where the code lives:
 - Server: netlify/functions/workplan.ts (a Netlify serverless Function).
 - Client: src/storage.ts (talks to the Function over HTTP).

The serverless Function (the only thing that touches Blobs):
 - It runs on Netlify's servers, not in the browser, so the Blobs access
   happens server-side where it is trusted.
 - It opens a named store with `getStore({ name: "workplan", consistency:
   "strong" })`. "workplan" is just the bucket name; "strong" consistency means
   a value written is immediately readable back (no propagation lag), which
   keeps saves and reloads in sync.
 - Netlify injects the Blobs credentials into the Function's runtime
   automatically, so no API keys appear anywhere in the code or the repo.

Per-user isolation (how one user can't see another's data):
 - The Function first identifies the signed-in user from their Netlify Identity
   session, then reads/writes a key namespaced to that user's id:
   `plan:<user.id>`. Because every user gets a distinct key, each account's
   workplan is stored and retrieved separately. If there is no valid session,
   the Function returns HTTP 401 and touches no data.

What is stored:
 - A single JSON value per user: the entire "workspace" object (all weeks,
   their tasks/sections, the active week, etc.). Reads use
   `store.get(key, { type: "json" })`; writes use `store.setJSON(key, value)`.

Request flow (client <-> Function <-> Blobs):
 - Load: on sign-in the browser GETs /.netlify/functions/workplan (sending the
   Identity cookie). The Function returns that user's stored JSON (or null for
   a brand-new user).
 - Save: on edits the browser POSTs the JSON back (debounced ~700ms so rapid
   edits collapse into one write). The Function validates it and calls setJSON.
 - A sync badge in the UI reflects this round-trip (Synced / Saving / Local
   only / Sync blocked).

Local fallback:
 - The browser also mirrors the data to localStorage. If the backend is
   unreachable (or during local dev without the Function), the app keeps
   working from the local copy; when the Function is reachable and the user is
   authenticated, the Blobs copy is authoritative and syncs across devices.

Why this approach:
 - It gives authenticated, per-user, cross-device persistence with essentially
   zero backend/database setup and no secrets in the codebase — Netlify manages
   the store's provisioning and access for us.
